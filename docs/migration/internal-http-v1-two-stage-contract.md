# Internal HTTP V1 Two-Stage Contract

## Purpose

This document records the internal v1 contract for the first LangGraph shadow
integration boundary.

The contract keeps:

- n8n as the official path;
- LangGraph as offline shadow;
- two formal application entrypoints;
- no real SQL execution;
- no real Watson call;
- no browser-to-LangGraph call.

## Use Cases

### GenerateSqlUseCase

Runs the generation-only flow:

```text
receive_question
-> load_context
-> classify_intent
-> build_plan
-> generate_sql
-> security_gate
-> contract_gate
-> engine_preflight offline
-> repair_sql when repairable before human approval
-> security_gate
-> contract_gate
-> engine_preflight offline
-> response with revisable SQL
-> stop
```

It never calls `execute_sql`, `normalize_result`, or `serialize_result`.

### ExecuteApprovedSqlShadowUseCase

Runs the approved-SQL shadow validation flow:

```text
approved_sql input
-> security_gate
-> contract_gate
-> engine_preflight offline
-> validation response
-> stop
```

If offline preflight reports a repairable issue, `repair_sql` may produce a
proposal. The original approved SQL remains intact.

## Endpoints

- `POST /v1/internal/sql-agent/generate`
- `POST /v1/internal/sql-agent/execute-approved-shadow`

These endpoints are internal HTTP boundaries for a future Next.js BFF caller.
The browser must not call them directly. The legacy `/v1/sql-agent/query`
endpoint remains unchanged.

## Generate Request

Minimum fields:

- `contract_version`: `"1"`;
- `agent_run_id`: product run identifier;
- `question`: user question;
- `principal`: normalized non-secret principal;
- `correlation_metadata`: optional safe scalar metadata.

Credentials, cookies, tokens, API keys, DSNs, raw headers, and provider raw
responses are not accepted.

## Generate Response

Key fields:

- `contract_version`;
- `agent_run_id`;
- `run_id`;
- `status`;
- `sql`;
- `intent`;
- `plan_status`;
- sanitized gate and preflight summaries;
- sanitized errors.

The SQL is revisable and is not approved for execution by this response.

## Execute Approved Shadow Request

Minimum fields:

- `contract_version`: `"1"`;
- `agent_run_id`: product run identifier;
- `approved_sql`: exact SQL approved by the user;
- `principal`: normalized non-secret principal;
- `correlation_metadata`: optional safe scalar metadata.

The approved SQL is still treated as untrusted input and must pass gates and
offline preflight.

### Synthetic QueryPlan Adapter

The Execute Approved Shadow flow builds a synthetic `QueryPlan` from the approved
SQL only to satisfy the current `security_gate`, `contract_gate`, and offline
`engine_preflight` contracts. This adapter does not represent the original plan
that generated the SQL and must not be treated as independent evidence of
semantic equivalence between the original plan and the approved SQL. In this
flow, `contract_gate` validates against the synthetic adapter shape, not against
the original product generation context. A future contract may pass the real
original plan/context, but that is outside this microstep.
## Execute Approved Shadow Response

Key fields:

- `contract_version`;
- `agent_run_id`;
- `run_id`;
- `status`;
- `approved_sql_original`;
- sanitized validation summaries;
- optional `repaired_sql_proposal`;
- `requires_reapproval`;
- sanitized errors.

If `repaired_sql_proposal` exists because SQL changed after the original human
approval, `requires_reapproval` is `true`. The repaired SQL is evidence or a
proposal only and is not approved.

## Run Correlation

`agent_run_id` is the original product run identifier.

`run_id` is generated by LangGraph for each internal call.

They are correlated but not required to be equal. The relationship may be 1:N.

## Execution Boundary

This phase does not execute SQL, does not call Watson real, does not call n8n,
does not call Gemini real, does not create shadow persistence, and does not
change the original product.
